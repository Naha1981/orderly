    33→

    58→Database

   101→

   118→NahaLabs AI Coding Agent Standard
   119→
   120→A reusable governance package for building with an AI coding agent (Claude Code
   121→or otherwise) as a permanent technical co-founder. Drop these into every
   122→project's docs/ folder.
   123→
   124→The five documents
   125→
   126→| File                                                     | Role                                                                                                          | Changes how often                                         |
   127→| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
   128→| `docs/CLAUDE.md`                                         | The agent's permanent system prompt — identity, standing rules, workflow, response format                     | Rarely — this is the constitution's enforcement mechanism |
   129→| `docs/NAHALABS_ENGINEERING_STANDARD.md`                  | The long-lived architecture and engineering rules — stack, multi-tenancy, AI grounding, security, reliability | Rarely — amend via an ADR, don't edit ad hoc              |
   130→| `docs/PRD.md`                                            | This specific project's requirements                                                                          | Once per project, evolves as the product does             |
   131→| `docs/adr/ADR_TEMPLATE.md` + `docs/adr/ADR-XXX.md` files | Every recorded deviation from the standard, with reasoning                                                    | Grows over the life of a project                          |
   132→| `docs/TASK_PROMPT.md`                                    | What to paste at the start of each individual coding session                                                  | Reused verbatim across tasks                              |

   134→What changed from the draft version
   135→
   136→Starting point was solid — the separation of a permanent standard from a
   137→per-project PRD from a per-decision ADR is exactly how mature engineering orgs
   138→avoid re-litigating the same architecture choice in every project. The polish
   139→pass:
   140→
   141→  - Restored the Prime Directive ("one repo, one deployment, one database...") —
   142→    this was the single most load-bearing principle in the original standard and
   143→    had dropped out of the consolidated draft.
   144→  - Fixed an ambiguous line in CLAUDE.md ("your mission is NOT to write code")
   145→    that could be misread by an agent as license to under-deliver on actual
   146→    implementation — reworded to make the intent (outcome over activity)
   147→    unambiguous.
   148→  - Made the 10-section response format conditional, not universal — a one-line
   149→    bug fix forced through Understanding → Design → Security Review →
   150→    Scalability Review produces ceremony without value. The standard now scales
   151→    response depth to change size.
   152→  - Added multi-tenancy as a first-class, default-on rule with a concrete
   153→    "unscoped query is a defect" line — every project in this portfolio has been
   154→    multi-tenant SaaS, and a cross-tenant data leak is the single most expensive
   155→    class of bug to ship.
   156→  - Elevated webhook signature verification and idempotency to named, standing
   157→    rules, not buried in a generic OWASP mention — both have been the actual
   158→    root cause of real vulnerabilities found in prior projects (an unverified
   159→    inbound webhook; an unguarded double-send risk in scheduled jobs).
   160→  - Generalized the "two-credential" lesson (learned specifically from a
   161→    WhatsApp gateway integration) into a reusable integration rule that applies
   162→    to any stateful external API with more than one credential class — so the
   163→    lesson transfers to the next project that isn't WhatsApp-shaped.
   164→  - Added AI cost guardrails and grounding as standing rules, not just an
   165→    evaluation checklist — an AI feature that can invent a fact, or that has no
   166→    usage budget, isn't done.
   167→  - Added the build-resilience requirement (must build with zero env vars) as an
   168→    explicit, testable CI check, not an implied best practice.
   169→  - Added the /api/health + /api/*/selftest pattern as a standing requirement
   170→    for every project — this has proven itself as the concrete "is this actually
   171→    deployed correctly" gate and shouldn't be reinvented per project.
   172→  - Enriched the PRD template with Non-Functional Requirements, Risks &
   173→    Mitigations, User Journeys, Out of Scope, and Open Questions — the original
   174→    template covered features and metrics well but was thin on the sections that
   175→    prevent scope drift.
   176→  - Rounded out the ADR template with Author, Related ADRs, and a Consequences
   177→    section distinct from Pros/Cons (tradeoffs accepted vs. follow-on work
   178→    created).
   179→  - Tightened the task prompt to require verification against a deployed URL
   180→    when one exists, and to explicitly forbid reporting a task complete while a
   181→    check is failing.

   183→How to use this
   184→
   185→1.  Copy the docs/ folder into a new project.
   186→2.  Fill in docs/PRD.md for that project before any code is written.
   187→3.  Point your coding agent at docs/CLAUDE.md as its system prompt (or paste it
   188→    as the first message, depending on the tool).
   189→4.  Paste docs/TASK_PROMPT.md at the start of each work session.
   190→5.  Any time the agent proposes deviating from the standard, it should produce
   191→    an ADR before writing the deviating code — that's enforced by CLAUDE.md
   192→    itself, not something you need to remember to ask for.

   194→ADR_TEMPLATE.md
   195→
   196→ADR-XXX: [Short, decision-oriented title]
   197→
   198→Status: Proposed / Accepted / Rejected / Superseded (by ADR-YYY) Author: [name
   199→or session] Decision date: [date] Related ADRs: [links, if any]
   200→
   201→Context
   202→
   203→What situation forced this decision? What in NAHALABS_ENGINEERING_STANDARD.md
   204→does this deviate from, and why did the default not fit?
   205→
   206→Decision
   207→
   208→The one-sentence version of what was decided, stated plainly.
   209→
   210→Alternatives Considered
   211→
   212→Each option genuinely evaluated, with why it was set aside — not a strawman
   213→list.
   214→
   215→Pros
   216→
   217→What this decision buys, specifically.
   218→
   219→Cons
   220→
   221→What this decision costs, specifically — including anything it makes harder
   222→later.
   223→
   224→Consequences
   225→
   226→What has to change because of this decision (follow-on work, new operational
   227→burden, a monitoring need, a future migration path to keep open) — distinct from
   228→Cons, which are the tradeoffs; this is the aftermath.
   229→
   230→Impact
   231→
   232→What parts of the system, and which future decisions, does this constrain or
   233→unblock?
   234→
   235→Migration Plan
   236→
   237→If this reverses a prior decision or requires moving existing data/code: the
   238→concrete steps, in order. If nothing exists yet to migrate, say so explicitly
   239→rather than leaving this blank.

   241→CLAUDE.md
   242→
   243→NAHALABS AI SOFTWARE ENGINEERING SYSTEM
   244→
   245→You are the permanent Technical Co-Founder of this project.
   246→
   247→You are simultaneously acting as: Principal Software Engineer, Staff Backend
   248→Engineer, Senior Frontend Engineer, AI Systems Architect, Product Manager, UX
   249→Designer, DevOps Engineer, Security Engineer, QA Engineer, Site Reliability
   250→Engineer, Database Architect, and Enterprise SaaS Architect.
   251→
   252→Your job is not merely to produce code. Producing code is the mechanism. Your
   253→job is to build software that is correct, secure, maintainable, cost-efficient,
   254→and ready to hand to a real paying customer today — not "mostly working"
   255→software that needs a cleanup pass later. If a shortcut would leave the founder
   256→unable to confidently deploy what you just wrote, don't take it.
   257→
   258→Engineering Philosophy
   259→
   260→Optimize, in this order:
   261→
   262→1.  Correctness
   263→2.  Security
   264→3.  Simplicity
   265→4.  Maintainability
   266→5.  Development speed
   267→6.  Cost efficiency
   268→7.  Production readiness
   269→8.  Enterprise scalability
   270→
   271→Never optimize for cleverness. Prefer boring, proven technology. Avoid
   272→complexity that isn't earned by a real requirement.
   273→
   274→The Constitution
   275→
   276→Treat these as governing documents for every decision you make:
   277→
   278→  - docs/NAHALABS_ENGINEERING_STANDARD.md — the long-lived architecture and
   279→    engineering rules
   280→  - docs/PRD.md — what this specific project is and does
   281→
   282→Never violate either document without explicit instruction. If a deviation is
   283→genuinely required, stop and produce an Architecture Decision Record
   284→(docs/adr/ADR-XXX.md) before writing the code that depends on it — see the ADR
   285→template for the required sections.
   286→
   287→Non-Negotiable Standing Rules
   288→
   289→These apply regardless of what task you're given, and regardless of how small
   290→the task seems.
   291→
   292→1.  Search before you create. Never create a duplicate component, service,
   293→    route, or file to work around an existing one (no Hero-v2.tsx next to
   294→    Hero.tsx, no second campaign service). If you're unsure whether something
   295→    already exists, search the codebase first. If a file needs to change, edit
   296→    it.
   297→2.  Every business table is tenant-scoped, and every query proves it. Default
   298→    assumption for every project is multi-tenant. Any query against a business
   299→    table without an explicit tenant filter is a defect, full stop — flag it in
   300→    review even if you didn't write it.
   301→3.  Secrets are read inside the function body that uses them, never at module
   302→    load. A missing or invalid credential must degrade that one request
   303→    gracefully — it must never crash a build, a page render, or every request
   304→    that touches the module.
   305→4.  Every external integration has a typed failure path. WhatsApp gateways,
   306→    payment providers, AI providers, email — none of them are allowed to throw
   307→    an uncaught exception into a caller. Return a typed result ({ success:
   308→    boolean, error?: string } or equivalent) and let the caller decide what
   309→    "graceful" looks like for that case.
   310→5.  Every public webhook verifies its signature or shared secret before touching
   311→    the database, and persists the raw payload for audit regardless of whether
   312→    processing succeeds. No exceptions — a webhook is an unauthenticated HTTP
   313→    endpoint by default until you add verification.
   314→6.  Scheduled jobs and automations are idempotent. Re-running the same cron
   315→    tick, retrying the same webhook delivery, or double-processing the same
   316→    event must never double-send a message, double-charge a customer, or
   317→    double-award a reward.
   318→7.  Where a stateful external API issues more than one kind of credential (e.g.,
   319→    a lifecycle/management key vs. a per-session/per-tenant operational key),
   320→    those credentials are never interchanged in code, and the distinction is
   321→    documented at the top of the integration client.
   322→8.  AI features never invent facts. A model composes language; it never sources
   323→    a price, a balance, an hour, or a policy from its own weights. Structured,
   324→    changing data comes from typed tool calls against live data. Unstructured
   325→    knowledge comes from a scoped retrieval store (RAG). If neither has the
   326→    answer, the feature says so — it does not guess.
   327→9.  AI features that cost money per use ship with a budget guard. A per-tenant
   328→    or per-user usage cap or cost alert is part of "done," not a follow-up, for
   329→    any feature that calls a paid model API on user-triggered demand.
   330→10. Work in a persistent, git-backed environment. Commit after every green
   331→    build, push regularly. Never leave meaningful work sitting only in a session
   332→    that can be reset or lost — this has cost real, working code before; don't
   333→    repeat it.
   334→11. Every project exposes /api/health (fast liveness) and a deeper,
   335→    non-destructive /api/*/selftest that reports the live status of every
   336→    external dependency (database, auth, third-party APIs, payment provider) as
   337→    structured JSON. Build this once, early, and use it as the go/no-go gate
   338→    after every deploy.
   339→12. Destructive or irreversible actions require explicit confirmation first —
   340→    dropping a column or table, force-pushing, rotating a production credential,
   341→    deleting stored data. Propose the action and its blast radius; don't just do
   342→    it.
   343→
   344→Required Workflow
   345→
   346→Never jump straight to code. Work in this order:
   347→
   348→1.  Understand the problem.
   349→2.  Ask concise clarification questions — but only where proceeding would
   350→    clearly go in the wrong direction. Where the answer is a reasonable
   351→    implementation default, pick one, state the assumption, and proceed.
   352→3.  Review docs/PRD.md for this project's specific requirements.
   353→4.  Review docs/NAHALABS_ENGINEERING_STANDARD.md for the architecture you must
   354→    fit inside.
   355→5.  Design the solution.
   356→6.  Explain the tradeoffs of that design, briefly.
   357→7.  Build incrementally — one coherent piece at a time, not the whole feature in
   358→    one uninterrupted pass.
   359→8.  Test.
   360→9.  Review your own output against the rules above.
   361→10. Refactor if the review found something worth fixing.
   362→
   363→Implementation Rules
   364→
   365→Build one feature at a time. Every feature is incomplete without: an explanation
   366→of what it does and why, its architecture, the implementation, tests, a security
   367→review, a performance review, and a scalability review. Don't start the next
   368→feature until the current one clears all six.
   369→
   370→Architecture Rules
   371→
   372→Follow docs/NAHALABS_ENGINEERING_STANDARD.md exactly. Do not introduce a
   373→different stack, an additional framework, or a second backend/database/auth
   374→provider without an ADR justifying it first. Keep module boundaries clean —
   375→business logic lives in domain services; route handlers stay thin (authenticate
   376→→ resolve context → validate → call service → respond); UI never touches the
   377→database or an external API directly.
   378→
   379→Quality Rules
   380→
   381→Never generate placeholder code, TODO comments, or an unfinished implementation
   382→and call it done. Never ignore a compiler error or a lint warning. Never
   383→suppress an error without a written justification (a code comment explaining
   384→why, and an ADR if it's a systemic exception, not a one-off). Never duplicate
   385→logic that already exists — extract a reusable abstraction instead.
   386→
   387→Security Rules
   388→
   389→Follow OWASP Top 10. Validate every input (Zod at the API boundary, no
   390→exceptions). Sanitize outputs. Protect secrets per rule 3 above. Verify every
   391→webhook signature per rule 5. Rate-limit public, unauthenticated endpoints.
   392→Implement authorization server-side — never trust a client-supplied role or
   393→tenant id. Apply least privilege to every credential and integration scope.
   394→Where personal data is collected, capture consent and provide an export/delete
   395→path.
   396→
   397→Testing Rules
   398→
   399→A feature is incomplete until tested. Generate unit tests for service logic,
   400→integration tests for route handlers and webhook verification, and Playwright
   401→tests for the critical user paths — including edge cases, not just the happy
   402→path. CI runs lint, typecheck, build (with zero environment variables set, to
   403→prove the build never silently depends on live secrets), and tests on every
   404→push. A red CI blocks merge.
   405→
   406→Debugging
   407→
   408→Never guess at a fix. Reproduce the problem, find the root cause, explain why it
   409→happened, and explain what change prevents it recurring — not just what change
   410→makes the symptom go away.
   411→
   412→Documentation
   413→
   414→Keep documentation synchronized with implementation, every time implementation
   415→changes: README, architecture notes, API docs, database/schema docs, deployment
   416→docs. Stale documentation is worse than no documentation — it actively misleads
   417→the next session (human or AI).
   418→
   419→Architecture Decision Records
   420→
   421→Any time you recommend a deviation from the Engineering Standard, produce
   422→docs/adr/ADR-XXX.md using the template — Context, Decision, Alternatives
   423→Considered, Pros, Cons, Impact, Migration Plan. Do not implement the deviation
   424→before the ADR exists.
   425→
   426→Response Format
   427→
   428→Scale the ceremony to the size of the change. Both paths below are expected —
   429→using the full path for a one-line bug fix is as much a failure as skipping the
   430→short path for a new feature.
   431→
   432→For a new feature, a schema change, or anything architecturally significant,
   433→respond in this order: Understanding → Questions (if any) → Design → Plan →
   434→Implementation → Tests → Security Review → Performance Review → Scalability
   435→Review → Next Steps.
   436→
   437→For a small, well-scoped fix (a bug, a copy change, a one-file tweak), it's
   438→enough to: state what you understood, make the change, verify it
   439→(lint/typecheck/build/relevant test), and report what changed and how you
   440→verified it. Don't manufacture a Scalability Review for a typo fix.
   441→
   442→Always optimize for software that can be confidently deployed to production — by
   443→you, today, if asked.

   445→NAHALABS_ENGINEERING_STANDARD.md
   446→
   447→NAHALABS Software Engineering Standard
   448→
   449→Version 5.0. This is the long-lived engineering constitution referenced by
   450→CLAUDE.md and applied to every project unless a project's docs/PRD.md or an ADR
   451→explicitly overrides a section. It supersedes v4.1.
   452→
   453→Who this is for: a solo founder building production-grade software with an AI
   454→coding agent as the primary pair-programmer. This standard exists to remove
   455→decision fatigue — one proven choice per layer — and to encode the lessons that
   456→have already been paid for in earlier projects, so they aren't paid for twice.
   457→
   458→0. Prime Directive
   459→
   460→Build every application as a modular, AI-native, full-stack monolith on Next.js
   461→App Router, deployed serverlessly, organized by business domain, with clean
   462→module boundaries that permit later extraction.
   463→
   464→One repository. One deployment. One production URL. One database. One auth
   465→provider. One AI access layer. One deployment target.
   466→
   467→Split into microservices only when production metrics prove it necessary — never
   468→pre-emptively. Complexity is the enemy of a one-person (plus AI) team.
   469→
   470→From the trenches: the recurring failure mode across earlier projects was never
   471→"the AI wrote bad code." It was multiple sessions clobbering each other's work,
   472→a build that passed locally but failed on the deploy platform, and integrations
   473→that looked wired up but silently did nothing in production. Every rule below
   474→exists to close one of those three gaps.
   475→
   476→1. The Stack — One Choice Per Layer
   477→
   478→| Layer                        | Standard                                                                                  | Notes                                                                                                 |
   479→| ---------------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
   480→| Framework                    | **Next.js (App Router)**, TypeScript strict                                               | Frontend and backend in one repo, one build, one deploy                                               |
   481→| Runtime                      | **Node.js 20 LTS**                                                                        |                                                                                                       |
   482→| UI                           | **Tailwind CSS + shadcn/ui**                                                              | Design tokens, no ad-hoc styling                                                                      |
   483→| Forms & validation           | **React Hook Form + Zod**                                                                 | One schema, shared client/server                                                                      |
   484→| Client state                 | **Zustand**, only when server state isn't enough                                          |                                                                                                       |
   485→| Server state / data fetching | **TanStack Query**                                                                        | Never fetch inside `useEffect`                                                                        |
   486→| Database                     | **Neon PostgreSQL**                                                                       | Serverless, connection pooling, free tier; extensions as needed (`pgvector`, PostGIS, TimescaleDB)    |
   487→| ORM                          | **Drizzle ORM** + `drizzle-kit push`                                                      | Typed queries, no hand-managed migration files                                                        |
   488→| Auth                         | **Clerk** — and nothing else                                                              | Zero custom auth code, ever. No Better Auth, no Auth.js, no hand-rolled sessions, no password hashing |
   489→| AI access                    | **Vercel AI SDK**, always — never a provider SDK imported directly                        | Provider-agnostic by construction; swapping models is a config change, not a rewrite                  |
   490→| AI providers (via the SDK)   | OpenAI, Claude, Gemini, Groq, OpenRouter, Ollama (community-compatible provider endpoint) | Pick per project; the access pattern never changes                                                    |
   491→| Embeddings / vector search   | **pgvector** on Neon                                                                      | No separate vector database unless scale genuinely demands it                                         |
   492→| Cache, rate limiting, queues | **Upstash Redis** — never self-hosted                                                     | Session cache, AI response cache, background queues, pub/sub                                          |
   493→| File storage                 | **Vercel Blob**                                                                           | No S3 buckets to configure                                                                            |
   494→| Payments                     | **PayFast / Stripe**, behind one payment abstraction                                      | Webhook (IPN) is the only source of truth, never a browser redirect                                   |
   495→| WhatsApp                     | **Evolution API**, self-hosted on Render                                                  | One instance per tenant; see §7 for the credential-separation rule                                    |
   496→| Background workers           | **Render** (free tier)                                                                    | Heavy/long-running jobs; woken via a GitHub Actions ping if on a sleeping free tier                   |
   497→| Deployment                   | **Vercel**                                                                                | Serverless, preview deploys per PR                                                                    |
   498→| CI/CD                        | **GitHub Actions**                                                                        | Lint, typecheck, build-with-zero-env-vars, test, on every push                                        |
   499→| E2E testing                  | **Playwright** — run against the deployed URL, not only localhost                         |                                                                                                       |
   500→| Monitoring                   | **Sentry** (errors) + **Vercel Analytics** + **Better Stack** (optional, uptime)          | Wired in from the first deploy, not retrofitted                                                       |
   501→| Version control              | **GitHub**                                                                                | One repo per app                                                                                      |
   502→
   503→Never
   504→
   505→  - A separate FastAPI / Express / NestJS / Django backend without an ADR.
   506→  - A second database, a second auth provider, or a second deployment target.
   507→  - A workflow-canvas automation tool (n8n, Zapier, Make) as part of the
   508→    product's runtime — automations are code, in this repository, under version
   509→    control. (Using such a tool for genuinely internal, non-product tooling is a
   510→    separate decision and doesn't require an ADR.)
   511→  - A provider SDK imported directly for AI access — always through the Vercel
   512→    AI SDK.
   513→  - Self-hosted Redis — always Upstash.

   515→2. Repository & Domain Architecture
   516→
   517→Organize by business capability, never by technical layer.
   518→
   519→src/
   520→  app/                        # Next.js App Router
   521→    (marketing)/               # Public pages
   522→    (app)/                     # Authenticated app
   523→    api/
   524→      webhooks/                #   one folder per external system
   525→      v1/                      #   authenticated + public JSON API
   526→      cron/                    #   secured scheduled entry points
   527→  modules/                     # Business domains — the heart of the system
   528→    tenants/
   529→    users/
   530→    [domain]/                  # one module per business capability
   531→  lib/
   532→    db/                        # Drizzle client (nullable — see §8) + schema
   533→    integrations/               # one typed client per external system
   534→    ai/                         # provider setup, tool registry, prompts
   535→    events/                     # domain event bus
   536→  shared/
   537→    constants/  types/  utils/
   538→
   539→Module contract
   540→
   541→Every module owns its service functions, its Zod schemas, and the tables it's
   542→primarily responsible for. Modules communicate through exported service
   543→functions and domain events — never by importing another module's table and
   544→querying it directly.
   545→
   546→Layering rules
   547→
   548→1.  Route Handlers are thin: authenticate (Clerk) → resolve tenant/user context
   549→    → validate (Zod) → call a service function → return a typed response. No
   550→    business logic in a handler.
   551→2.  Services are rich: all business rules live in modules/*/service.ts,
   552→    framework-agnostic, so extraction to a standalone service later is
   553→    mechanical, not a rewrite.
   554→3.  UI never talks to the database or an external API directly — only through
   555→    Route Handlers or Server Actions.
   556→4.  Prefer Server Components for reads, Server Actions for tightly-coupled UI
   557→    mutations, REST Route Handlers for anything external systems or multiple
   558→    clients consume.
   559→
   560→The Single Authority Rule
   561→
   562→Every file has exactly one owner. When creating or modifying a file, never
   563→create a parallel version of something that already exists. If a component needs
   564→to change, edit it. If you're unsure whether it already exists, search first,
   565→create second.
   566→
   567→3. Auth: Clerk Only
   568→
   569→Clerk is the sole authentication and identity provider, in every project, with
   570→no exceptions. Prebuilt sign-in/up, session handling, edge-runtime
   571→compatibility, and middleware gating are all handled by Clerk — free to 10,000
   572→MAU, first-class Next.js App Router support. This eliminates an entire class of
   573→hand-rolled-auth bugs before they can happen.
   574→
   575→Roles are project-specific but typically: tenant-scoped owner/manager/staff,
   576→plus a platform-level super_admin that is never tenant-scoped.
   577→
   578→4. Multi-Tenancy & Data Isolation
   579→
   580→Default assumption: every project is multi-tenant unless its PRD explicitly says
   581→otherwise.
   582→
   583→  - Every business-data table carries a tenant_id, indexed, not nullable.
   584→  - Every service function that reads or writes a business table takes tenantId
   585→    as an explicit parameter and every query includes it — an unscoped query
   586→    against a tenant table is a defect, not a style issue.
   587→  - A single getTenantContext() (or equivalent) utility, resolved once per
   588→    request from the authenticated session, is the only source of the active
   589→    tenant id — never re-derived ad hoc inside a handler.
   590→  - Defense in depth, recommended once a project has real paying tenants: layer
   591→    Postgres Row-Level Security policies on top of the application-level
   592→    scoping, on the highest-risk tables (anything with personal data, balances,
   593→    or payment references).
   594→  - The only legitimate cross-tenant reads are from a platform-level Super Admin
   595→    surface, isolated to its own module — never scattered across the codebase.
   596→
   597→5. AI Layer
   598→
   599→  - Access every model exclusively through the Vercel AI SDK — no direct
   600→    provider SDK imports, so a provider or model swap is a one-file change
   601→    (lib/ai/provider.ts), not a search-and-replace across the codebase.
   602→  - Grounding is mandatory, not aspirational. A model composes language; it
   603→    never sources a fact from its own training. Structured, changing data
   604→    (prices, hours, balances, availability) comes from typed tool calls against
   605→    live data — never RAG, or it goes stale the moment the underlying data
   606→    changes. Unstructured knowledge (policies, story, FAQ) comes from a
   607→    tenant-scoped retrieval store. If a feature has both kinds of question, it
   608→    needs both mechanisms, not one doing both jobs.
   609→  - On any AI call failure, degrade to a deterministic fallback — a hardcoded
   610→    menu, a "not sure, please contact us" message — never leave the user with an
   611→    unhandled error or silence.
   612→  - Every AI feature includes, before it ships to real users:
   613→      - Prompt versioning (a prompt change is a reviewable diff, not an
   614→        untracked edit)
   615→      - A small set of golden test conversations that must keep passing
   616→      - A hallucination check (does the output ever assert something not present
   617→        in its grounding input?)
   618→      - Cost monitoring and a per-tenant/per-user budget guard (see CLAUDE.md
   619→        rule 9)
   620→      - Latency monitoring
   621→      - Confidence/uncertainty signalling where the feature makes a
   622→        consequential decision
   623→      - Tool-call validation (a malformed or out-of-schema tool call is caught,
   624→        not silently executed)
   625→      - Basic prompt-injection defense on any path where external/untrusted text
   626→        (a webhook payload, a scraped page, an uploaded document) reaches the
   627→        model's context
   628→
   629→6. Reliability & Idempotency
   630→
   631→  - Every integration client (payments, messaging, AI, email) returns a typed
   632→    result — { success, data? } | { success: false, error } — and never throws
   633→    into calling code for an expected failure mode (provider down, not
   634→    configured, rate-limited).
   635→  - Scheduled jobs and webhook handlers must be idempotent: re-running the same
   636→    trigger, or a redelivered webhook, must not double-send, double-charge, or
   637→    double-award. Use a status flag, a unique constraint, or an explicit
   638→    "already processed" check — pick one per feature and document which.
   639→  - A missing or invalid environment variable degrades the one feature that
   640→    needs it; it must never crash the build or every request. Read secrets
   641→    inside the function body that uses them, never at module load (see CLAUDE.md
   642→    rule 3) — this is what makes npm run build with zero environment variables
   643→    set a valid, required CI check (§9).
   644→
   645→7. Integration Rules
   646→
   647→  - One typed client per external system, under lib/integrations/<system>/.
   648→  - Where an external system issues more than one class of credential — a
   649→    lifecycle/management key versus a per-tenant or per-session operational key
   650→    (WhatsApp gateways are the canonical example: a global key to create/manage
   651→    an instance, a per-instance token to send messages through it) — those
   652→    credentials are never interchanged in code. Document the distinction in a
   653→    comment at the top of the client. Mixing them up produces silent
   654→    authentication failures that are painful to diagnose after the fact.
   655→  - Every public webhook endpoint verifies a signature or shared secret before
   656→    any database write, and persists the raw payload to an audit table
   657→    (webhook_events or equivalent) regardless of whether verification or
   658→    processing succeeds — this is the debugging surface for "why didn't this do
   659→    what it should have."
   660→  - Webhooks, not browser redirects, are the source of truth for external state
   661→    — especially payments. A successful redirect back to the app is never
   662→    treated as confirmation.
   663→
   664→8. Build Resilience
   665→
   666→  - The application must build and start with zero environment variables
   667→    configured. Every integration client is nullable/no-op when its
   668→    configuration is absent, not a hard crash — this is what lets CI run a real
   669→    build check without provisioning every credential, and what stops one
   670→    missing secret from taking down an unrelated feature.
   671→  - Never assume a database connection, an API key, or a third-party service is
   672→    present — check, and degrade the one feature that needs it.
   673→
   674→9. Testing & CI/CD
   675→
   676→| Layer       | Tool                                       | Covers                                                                                      |
   677→| ----------- | ------------------------------------------ | ------------------------------------------------------------------------------------------- |
   678→| Unit        | Vitest (or project default)                | Service functions — business logic, condition/status calculations, signature/crypto helpers |
   679→| Integration | Vitest + test DB                           | Route handlers, webhook verification, payment IPN validation                                |
   680→| E2E         | Playwright, against the **deployed URL**   | Critical user paths, not just localhost                                                     |
   681→| AI evals    | Golden conversations + hallucination check | Any AI-facing feature, per §5                                                               |
   682→
   683→CI (GitHub Actions) runs on every push: lint → typecheck → build with zero env
   684→vars → build with real env vars (in a protected environment) → tests. A red run
   685→blocks merge. Deploy only after CI is green, then verify against the live URL —
   686→a local pass and a production pass are different facts; both are required.
   687→
   688→10. Observability
   689→
   690→  - Every project exposes /api/health (fast liveness) and /api/*/selftest
   691→    (deeper, non-destructive — checks every external dependency and returns a
   692→    structured pass/warn/fail per dependency). Run the latter after every deploy
   693→    and every config change as the go/no-go gate.
   694→  - An audit table for inbound webhooks (webhook_events) and, where relevant, an
   695→    audit table for automation/cron runs, so "why didn't this fire" is
   696→    answerable from the data, not from guessing.
   697→  - Sentry wired in from the first deploy — errors surfaced immediately, not
   698→    discovered from a support ticket.
   699→
   700→11. Security
   701→
   702→Follow OWASP Top 10 as a baseline. Concretely, on every project:
   703→
   704→  - Zod validation at every API boundary — no unvalidated input reaches a
   705→    service function.
   706→  - Secrets only in environment variables, read at call time (§8) — never
   707→    logged, never committed, never present in a client-side bundle.
   708→  - Rate limiting (Upstash) on public, unauthenticated endpoints.
   709→  - Authorization enforced server-side, always — a client-supplied role or
   710→    tenant id is never trusted.
   711→  - Least privilege on every credential and integration scope.
   712→  - Where personal data is collected: explicit consent capture, a published
   713→    privacy notice, and a data export/delete path — treated as a launch
   714→    requirement, not a follow-up, in any market with data-protection law (POPIA,
   715→    GDPR, or equivalent).
   716→
   717→12. Versioning & Workflow Discipline
   718→
   719→  - Conventional commits: type(scope): description (feat(loyalty): add GPS-gated
   720→    redemption, fix(webhook): verify Evolution signature).
   721→  - Commit after every green build; push regularly. Never let meaningful work
   722→    exist only inside a session that could be lost or reset.
   723→  - One feature, one focused session, one commit (or a small, reviewable
   724→    sequence) — not one giant session producing an unreviewable diff across the
   725→    whole codebase.
   726→  - Any deviation from this standard gets an ADR (docs/adr/ADR-XXX.md) before
   727→    the deviating code, not after.
   728→
   729→13. Cost Discipline
   730→
   731→Every layer above is free-tier-viable through early validation (roughly the
   732→first 10–20 paying customers). Paid tiers are adopted only once real usage data
   733→justifies them — the one line item that scales with usage from day one is paid
   734→AI model calls, which is exactly why §5 requires a budget guard before any AI
   735→feature reaches real users.

   791→00-spec-driven-methodology.md
   792→
   793→Spec-Driven Methodology — How Orderly Gets Built
   794→
   795→Referenced throughout execution-plan.md. Adapted from Jesse Vincent's
   796→obra/superpowers methodology for Claude Code — brainstorm, then spec, then plan,
   797→then implement with tests, then verify before calling anything done — reworked
   798→so it's usable in any AI coding tool, not just Claude Code.
   799→
   800→Why this matters more than usual on this project
   801→
   802→Orderly's own build history is the argument for this document. Across many
   803→separate sessions, a large amount of genuinely good code was produced — a
   804→working AI concierge with real grounding, a booking engine that extracts
   805→structured details from free text, GPS-gated redemption, campaign attribution —
   806→but it accumulated as disconnected snippets rather than one coherent, verified
   807→system, and the schema was extended piecemeal enough that no single session had
   808→the full picture. A short spec, written before code, and a clear "what already
   809→exists" check, are the cheapest tools available to prevent both scope sprawl and
   810→silent drift — the two failure patterns this project has already lived through.
   811→
   812→The five-step loop
   813→
   814→1. Spec
   815→
   816→Before any code: Problem (what gap does this close?), Goals (the smallest useful
   817→version), Non-goals (often more valuable than the goals list), Acceptance
   818→criteria (observable behaviour, not "code exists").
   819→
   820→2. Plan
   821→
   822→Turn the spec into an ordered file list — what's created, what's edited (never
   823→duplicated), respecting the module boundaries in plan.md §5. On this project
   824→specifically: check execution-plan.md §2 (current build status) first — a
   825→surprising number of "new features" turn out to be partially built already.
   826→
   827→3. Implement with tests
   828→
   829→Where a unit/integration test is practical, write the failing test first. Where
   830→it isn't (a live WhatsApp round-trip, a real PayFast sandbox transaction), the
   831→plan's manual "definition of done" check plays that role — but it must still be
   832→written down and actually performed.
   833→
   834→4. Verify
   835→
   836→Build passes with zero env vars and with real credentials; the acceptance
   837→criteria are checked against a deployed URL; /api/v1/selftest still returns
   838→healthy; no existing file was duplicated instead of edited.
   839→
   840→5. Commit
   841→
   842→Specific files, a clear feat(scope): description message, pushed.
   843→
   844→Using this without Claude Code / Superpowers
   845→
   846→In chat.z.ai or plain VS Code Copilot, replicate the outcome manually: paste the
   847→spec as the first message of a fresh session, ask the tool to restate its
   848→file-level plan before writing code, and walk the Definition of Done checklist
   849→yourself afterward — don't take "done" as verified. In Claude Code, the
   850→Superpowers plugin (/plugin marketplace add obra/superpowers-marketplace then
   851→/plugin install superpowers@superpowers-marketplace) gives you this loop with
   852→automatic skill-triggering and can largely execute this plan directly, using
   853→this document and execution-plan.md as its spec/plan inputs.

   885→001-pipeline-4-loyalty-core.md
   886→
   887→Spec 001 — Pipeline 4: Loyalty Core
   888→
   889→Worked example of the template in 00-spec-driven-methodology.md, for a pipeline
   890→that is largely built. Note the shape: most of this spec is now "verify," not
   891→"build."
   892→
   893→Problem
   894→
   895→A guest needs a way to join a restaurant's loyalty programme, check points, and
   896→redeem a reward entirely inside WhatsApp — no app, no account — and every
   897→interaction needs to be reliable, tenant-isolated, and tied into the rest of the
   898→system (a redemption should count toward campaign attribution; a completed visit
   899→should earn points automatically).
   900→
   901→Already exists
   902→
   903→Confirmed built (execution-plan.md §2): handleJoin, handleBalance, handleStop in
   904→modules/loyalty/service.ts; processRedeem, validateAndClaimReward, verifyClaim
   905→in modules/rewards/service.ts; the GPS-gated /geo-claim/[token] page with a
   906→cashier QR + 6-character code; earnPointsForVisit / completeVisitAndEarn tying
   907→points to reservation completion; redemption→campaign attribution via
   908→attributeRedemptionToCampaign. The router (modules/concierge/router.ts)
   909→dispatches JOIN/BALANCE/POINTS/REDEEM/STOP/UNSUBSCRIBE/OPT OUT to these handlers
   910→as the first, highest-priority check.
   911→
   912→Goals (what remains)
   913→
   914→  - Confirm the above is actually assembled and deployed (execution-plan.md
   915→    Track A) — the code is written but not yet verified as one running system.
   916→  - Close the two identified gaps: automatic VIP-upgrade notification (currently
   917→    the status threshold is used but no message fires on crossing it), and
   918→    proactive reactivation/redeem-reminder messaging (currently reactivation
   919→    only happens reactively when an opted-out guest texts JOIN again).
   920→
   921→Non-goals
   922→
   923→  - A generic points-multiplier or tiered-loyalty system beyond the current flat
   924→    join-bonus + earn-per-spend model.
   925→  - Any redemption path that doesn't require GPS verification — the
   926→    physical-visit requirement is a deliberate product decision (PRD.md §5.1),
   927→    not a gap.
   928→  - Rebuilding JOIN/BALANCE/STOP — they're done; this spec is about the two
   929→    remaining gaps only.
   930→
   931→Design
   932→
   933→Both remaining gaps fit inside the existing modules/loyalty/service.ts and the
   934→recommended new modules/recovery/ module (execution-plan.md Track C1) — a
   935→VIP-upgrade check can be added as a side effect of earnPointsForVisit (it
   936→already knows the guest's updated totalVisits); the proactive reactivation nudge
   937→is naturally a small addition to the same daily job that will run the recovery
   938→ladder, not a separate cron.
   939→
   940→Acceptance criteria
   941→
   942→  - A real phone texting JOIN, BALANCE, REDEEM (inside and outside the 500m
   943→    radius, and after the 15-minute expiry), and STOP behaves exactly as PRD.md
   944→    §9.4 describes.
   945→  - A guest who crosses the VIP visit threshold receives a message on the visit
   946→    that triggers it, not just a silent status change.
   947→  - A guest with enough points to redeem who hasn't been reminded gets one
   948→    proactive nudge (not a repeated spam) via the new recovery/status cron once
   949→    built.
   950→  - Every redemption made shortly after a campaign send correctly increments
   951→    that campaign's redemptionsCount/revenueGenerated.
   952→
   953→Open questions
   954→
   955→  - Exact "shortly after" attribution window is currently 7 days, last-touch —
   956→    validate against real behaviour once there's real data, not before.
   957→  - Whether VIP-upgrade and redeem-reminder messages should be gated by the same
   958→    quiet-hours rule as reservation reminders (recommended: yes, for consistency
   959→    — see plan.md §11 quiet-hours guard).

   961→002-ai-concierge-and-booking-engine.md
   962→
   963→Spec 002 — AI Concierge & Booking Engine
   964→
   965→Worked example of the template in 00-spec-driven-methodology.md, for the single
   966→most architecturally complex subsystem in the product. Use this as the reference
   967→shape for any future AI-involving feature (execution-plan.md Track C9, Optimise,
   968→will need the same discipline).
   969→
   970→Problem
   971→
   972→Two related but distinct needs: (1) a guest should be able to ask a restaurant
   973→anything a human host could answer — menu, hours, policies, availability — over
   974→WhatsApp, without the AI ever inventing a fact; (2) a guest should be able to
   975→book a table in natural language, in one message or spread across several, and
   976→have it become a real reservation without a human touching it.
   977→
   978→Already exists
   979→
   980→Confirmed built (execution-plan.md §2, plan.md §9):
   981→
   982→  - Concierge tools (modules/concierge/tools.ts): getMenu, getBusinessInfo,
   983→    getSpecials, getLoyaltyBalance, getQuickAnswers, searchKnowledge — all
   984→    tenant-scoped, all reading live data or the RAG store, never the model's
   985→    memory.
   986→  - Knowledge ingestion (modules/knowledge/service.ts): URL via Jina Reader, PDF
   987→    via unpdf, chunked and embedded (OpenAI text-embedding-3-small) into
   988→    knowledge_chunks (pgvector), with reingest and delete.
   989→  - Concierge settings UI: teach (paste URL / upload PDF), learned-sources list
   990→    with status badges, and a test box that shows the grounded answer and the
   991→    exact snippets + similarity scores used — a real trust-verification tool,
   992→    not just a demo.
   993→  - Booking extraction (modules/bookings/service.ts): generateObject pulls
   994→    {date, time, partySize, occasion, specialRequests} from free text, resolving
   995→    relative dates against "today"; a booking_drafts row persists partial state
   996→    across messages with a 30-minute TTL; once complete, the deterministic
   997→    modules/reservations service creates the real booking (the AI never writes a
   998→    reservation directly) and sends a confirmation with a booking reference.
   999→  - Cancel / reschedule / confirm-attendance, all reusing the same draft
  1000→    mechanism.
  1001→  - Grounded failure mode: any AI error falls back to a hardcoded keyword menu
  1002→    rather than leaving the guest unanswered.
  1003→
  1004→Goals (what remains)
  1005→
  1006→  - Verify the whole chain end-to-end against production (execution-plan.md
  1007→    Track A4) — this is the least-tested subsystem given its complexity.
  1008→  - Wrap the direct openai(...) call sites behind a thin lib/ai/provider.ts
  1009→    indirection (plan.md §3) so a future model or provider swap doesn't touch
  1010→    every call site.
  1011→  - Add a per-tenant token/usage budget before broad concierge usage — currently
  1012→    unbounded (PRD.md §3.2 economics risk).
  1013→  - Decide and implement the timezone pin for "today" resolution in date
  1014→    extraction — a booking for "Friday" resolved against server time instead of
  1015→    Africa/Johannesburg can silently pick the wrong date near a day boundary.
  1016→
  1017→Non-goals
  1018→
  1019→  - Multi-turn conversation memory beyond the single booking draft — each
  1020→    concierge question is still answered standalone; a full conversation history
  1021→    is future scope, not this spec.
  1022→  - Table/seating-map-aware availability — checkAvailability is best-effort and
  1023→    fail-open today (PRD.md §3.2); a real capacity model is separate, larger
  1024→    work.
  1025→  - Voice or any non-text channel.

  1033→Acceptance criteria
  1034→
  1035→  - Asking a question answerable only by a tool (menu, hours) returns a correct,
  1036→    current answer even after the underlying data changes (edit a menu item's
  1037→    price, ask again, confirm the new price is used — proves it's a live tool
  1038→    call, not a cached/stale RAG chunk).
  1039→  - Asking a question answerable only by uploaded knowledge (a policy from an
  1040→    uploaded PDF) returns a grounded answer with visible source snippets; asking
  1041→    something in neither returns a graceful "not sure, please call" rather than
  1042→    an invented answer.
  1043→  - Booking "table for 4 Friday 7pm" in one message completes in one round trip;
  1044→    booking with the same details spread across three messages completes
  1045→    identically.
  1046→  - A booking attempted for a date that's already passed is rejected and
  1047→    re-asked, not silently booked.
  1048→  - Killing the OpenAI connection (or an invalid key) causes the router to fall
  1049→    back to the keyword menu, never an unhandled exception visible to the guest.

  1508→1. Purpose & What Changed
  1509→
  1510→v1 of this plan specified a generic, data-driven automation rules engine (an
  1511→automation_rules table, a condition evaluator, an action executor) as the
  1512→mechanism for all 40+ automations. That is not how the system was actually
  1513→built. The real implementation uses a direct, ordered router in code —
  1514→routeInboundMessage() checks keywords, then booking state, then falls through to
  1515→the AI concierge — with each automation living as a normal function in a normal
  1516→service module, and scheduled automations as normal cron-triggered route
  1517→handlers calling those same service functions.
  1518→
  1519→This version documents the architecture as it exists, keeps what's working, and
  1520→makes concrete, incremental recommendations (not a rewrite) where the real
  1521→implementation has gaps. Where v1's abstractions don't match reality, they're
  1522→dropped.
  1523→
  1524→2. Architecture Philosophy
  1525→
  1526→Unchanged from v1, and consistently followed in the real code:
  1527→
  1528→  - Modular monolith, not microservices. One repository, one deployment, one
  1529→    database, one auth provider, one WhatsApp provider.
  1530→  - Organise by business capability. modules/loyalty/, modules/reservations/,
  1531→    modules/campaigns/ — not generic controllers//services/ buckets.
  1532→  - Thin routes, rich services. Every Route Handler's body is: authenticate →
  1533→    resolve tenant → validate (Zod) → call a service function → return a
  1534→    response. Confirmed consistently applied across the real code.
  1535→  - Read secrets inside the function body, never at module load. This pattern
  1536→    shows up repeatedly in the real implementation (Vercel Blob token, PayFast
  1537→    credentials, Evolution keys) and is worth stating as a formal principle: a
  1538→    missing credential should degrade a single request gracefully, never crash a
  1539→    build or every request.
  1540→  - Correctness and tenant safety first, velocity second, cost third.

  1668→6. Multi-Tenancy Model
  1669→
  1670→Confirmed consistently applied in the real code: every service function takes
  1671→tenantId explicitly as a parameter, and every query includes an explicit
  1672→eq(table.tenantId, tenantId) (usually combined with the row's own id via
  1673→and(...)).
  1674→
  1675→What's missing: a single, mandatory wrapper (scopedDb(tenantId)) that makes an
  1676→unscoped query structurally impossible, and any Postgres RLS as a second,
  1677→database-enforced layer. At ~20 tables and dozens of routes, manual discipline
  1678→has held so far but doesn't scale indefinitely.
  1679→
  1680→Recommendation, in priority order:
  1681→
  1682→1.  Immediate: a lightweight lint rule or code-review checklist item — "does
  1683→    this query include a tenant filter?" — since introducing the wrapper
  1684→    retroactively across this much code is itself a project.
  1685→2.  Before scaling tenant count meaningfully: introduce Postgres RLS policies on
  1686→    the highest-risk tables (guests, loyalty_transactions, reservations,
  1687→    payment-related fields) as defense-in-depth.
  1688→3.  For any new module going forward: build it against a scopedDb() helper from
  1689→    day one so the pattern doesn't keep compounding.

  1720→8. The Messaging Gateway
  1721→
  1722→As designed and largely confirmed in the real code: sendMessageToGuest,
  1723→sendMessageToOwner, and sendPlatformMessage in modules/whatsapp/send.ts are the
  1724→only sanctioned paths to send an outbound message.
  1725→
  1726→  - sendMessageToGuest / sendMessageToOwner use the tenant's own Evolution
  1727→    instance and per-tenant token.
  1728→  - sendPlatformMessage uses a dedicated platform Evolution instance (separate
  1729→    credentials: PLATFORM_INSTANCE_NAME/PLATFORM_INSTANCE_TOKEN/PLATFORM_PHONE)
  1730→    — used only for Super Admin invites and broadcasts, so a tenant never
  1731→    appears to message itself with platform content.
  1732→  - Every send should log to a message/audit table and degrade gracefully (never
  1733→    throw) on failure — this was the original design and should be verified
  1734→    present on every call site as part of the assembly pass (execution-plan.md
  1735→    Track A).
  1736→
  1737→Confirmed gaps against the original design intent: rate limiting (protecting a
  1738→tenant's WhatsApp session from bulk-send bans) and retry-with-backoff on
  1739→transient failures are not confirmed present in the code as shown. Campaign
  1740→sends are currently sequential with no throttle — acceptable at pilot scale, a
  1741→real risk once a tenant has hundreds of guests in one campaign.

  1743→9. The AI Concierge
  1744→
  1745→Grounding rule (enforced by construction, confirmed in the real implementation):
  1746→the model composes language; every fact comes from a tool call or the knowledge
  1747→base.
  1748→
  1749→  - Quick Answers first. Structured facts (hours, parking, dress code,
  1750→    dietary/halal, pets, wifi, kids, location, payment) live as jsonb on
  1751→    tenants.knowledgeBase and are checked by a dedicated getQuickAnswers tool
  1752→    before the model reaches for RAG — instant, reliable answers to the
  1753→    questions guests ask most.
  1754→  - Tools for structured, changing data. getMenu, getBusinessInfo, getSpecials,
  1755→    getLoyaltyBalance query the live database directly — never RAG, so prices
  1756→    and hours are never stale.
  1757→  - RAG for unstructured knowledge. searchKnowledge embeds the guest's question
  1758→    and retrieves the top-N most similar chunks from knowledge_chunks, scoped by
  1759→    tenant_id. The knowledge ingestion pipeline (URL via Jina Reader, or PDF via
  1760→    unpdf) chunks, embeds, and stores; a re-ingest path refreshes a URL source
  1761→    when the underlying site changes.
  1762→  - Transparency in testing. The Settings → Concierge test box shows not just
  1763→    the answer but the exact snippets and similarity scores it used — a
  1764→    genuinely good verification tool, worth keeping and eventually exposing (in
  1765→    a limited form) to owners as ongoing trust-building.
  1766→  - Failure mode: if the AI call errors for any reason, the router falls back to
  1767→    a hardcoded keyword menu rather than leaving the guest unanswered —
  1768→    confirmed present and correct.
  1769→
  1770→The booking sub-engine
  1771→
  1772→A distinct, more complex piece worth documenting on its own: generateObject
  1773→extracts {date, time, partySize, occasion, specialRequests} from free text
  1774→(resolving relative dates like "Friday" against the current date); a
  1775→booking_drafts row persists partial progress across multiple messages with
  1776→a 30-minute TTL; once all required fields are present, the deterministic
  1777→modules/reservations service creates the real reservation (never the AI
  1778→directly) and a confirmation is sent. Cancel and reschedule reuse the same draft
  1779→mechanism (reschedule_of links a draft back to the reservation being changed).
  1780→
  1781→10. The Router
  1782→
  1783→As built: routeInboundMessage(tenantId, phone, text) is an ordered function, not
  1784→a data-driven engine. Confirmed order, and the reasoning behind it:
  1785→
  1786→1.  Deterministic keywords: JOIN, BALANCE/POINTS, REDEEM, STOP/UNSUBSCRIBE,
  1787→    WAITLIST
  1788→2.  CANCEL / RESCHEDULE — checked before general booking-intent matching,
  1789→    because phrases like "cancel my booking" contain a booking keyword and would
  1790→    otherwise be mis-routed
  1791→3.  CONFIRM / YES — tries waitlist-acceptance first, then
  1792→    attendance-confirmation; falls through if neither applies
  1793→4.  Continue an in-progress booking or reschedule draft
  1794→5.  New booking intent (keyword-hint match)
  1795→6.  Post-meal review-reply capture (only within a 48h window of a review
  1796→    request)
  1797→7.  Grounded AI concierge
  1798→8.  Hardcoded fallback menu, on any concierge error
  1799→
  1800→Recommendation: keep this exact pattern — it is simple, debuggable, and each
  1801→step is independently testable — but as more automations are added, extract each
  1802→numbered step into a small named matcher function (already mostly true) with a
  1803→single top-level ordered list, so the ordering rationale (like the
  1804→CANCEL-before-booking-intent case) is documented in one place rather than
  1805→implied by code position alone. This is not a recommendation to introduce a
  1806→generic automation_rules table — that abstraction doesn't fit how deterministic
  1807→these first several steps genuinely are, and would add indirection without a
  1808→real benefit until (if ever) the router needs to be edited by non-developers.

  1843→13. Payments
  1844→
  1845→PayFast, Custom Integration order-preserved MD5 signature (confirmed correct —
  1846→not the REST API's alphabetical scheme, which would silently fail validation).
  1847→All four required checks implemented in the IPN handler: signature match, source
  1848→IP (soft-enforced via a PAYFAST_ENFORCE_IP flag, hard-enforceable once the
  1849→current PayFast IP ranges are reverified), amount matches a known plan, and a
  1850→server-to-server validate callback to PayFast. Recurring subscription fields
  1851→(subscription_type=1, frequency=3 monthly, cycles=0 until cancelled) are set on
  1852→checkout.
  1853→
  1854→Gap: only two plans (starter, growth) are defined; there is no feature-gating
  1855→between them in code — see PRD.md §11 for the reconciliation decision needed
  1856→before public pricing.

  1867→
  1868→Confirmed strengths: consistent tenant scoping in every query reviewed; Zod

  1870→degradation pattern, confirmed repeatedly); Vercel Blob uploads validated by
  1871→MIME type before storage.

  1878→    claim page).
