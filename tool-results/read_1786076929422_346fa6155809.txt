  1508→1. Purpose & What Changed
  1509→
  1510→v1 of this plan specified a generic, data-driven automation rules engine (an
  1511→automation_rules table, a condition evaluator, an action executor) as the
  1512→mechanism for all 40+ automations. That is not how the system was actually
  1513→built. The real implementation uses a direct, ordered router in code —
  1514→routeInboundMessage() checks keywords, then booking state, then falls through to
  1515→the AI concierge — with each automation living as a normal function in a normal
  1516→service module, and scheduled automations as normal cron-triggered route
  1517→handlers calling those same service functions.
  1518→
  1519→This version documents the architecture as it exists, keeps what's working, and
  1520→makes concrete, incremental recommendations (not a rewrite) where the real
  1521→implementation has gaps. Where v1's abstractions don't match reality, they're
  1522→dropped.
  1523→
  1524→2. Architecture Philosophy
  1525→
  1526→Unchanged from v1, and consistently followed in the real code:
  1527→
  1528→  - Modular monolith, not microservices. One repository, one deployment, one
  1529→    database, one auth provider, one WhatsApp provider.
  1530→  - Organise by business capability. modules/loyalty/, modules/reservations/,
  1531→    modules/campaigns/ — not generic controllers//services/ buckets.
  1532→  - Thin routes, rich services. Every Route Handler's body is: authenticate →
  1533→    resolve tenant → validate (Zod) → call a service function → return a
  1534→    response. Confirmed consistently applied across the real code.
  1535→  - Read secrets inside the function body, never at module load. This pattern
  1536→    shows up repeatedly in the real implementation (Vercel Blob token, PayFast
  1537→    credentials, Evolution keys) and is worth stating as a formal principle: a
  1538→    missing credential should degrade a single request gracefully, never crash a
  1539→    build or every request.
  1540→  - Correctness and tenant safety first, velocity second, cost third.

  1668→6. Multi-Tenancy Model
  1669→
  1670→Confirmed consistently applied in the real code: every service function takes
  1671→tenantId explicitly as a parameter, and every query includes an explicit
  1672→eq(table.tenantId, tenantId) (usually combined with the row's own id via
  1673→and(...)).
  1674→
  1675→What's missing: a single, mandatory wrapper (scopedDb(tenantId)) that makes an
  1676→unscoped query structurally impossible, and any Postgres RLS as a second,
  1677→database-enforced layer. At ~20 tables and dozens of routes, manual discipline
  1678→has held so far but doesn't scale indefinitely.
  1679→
  1680→Recommendation, in priority order:
  1681→
  1682→1.  Immediate: a lightweight lint rule or code-review checklist item — "does
  1683→    this query include a tenant filter?" — since introducing the wrapper
  1684→    retroactively across this much code is itself a project.
  1685→2.  Before scaling tenant count meaningfully: introduce Postgres RLS policies on
  1686→    the highest-risk tables (guests, loyalty_transactions, reservations,
  1687→    payment-related fields) as defense-in-depth.
  1688→3.  For any new module going forward: build it against a scopedDb() helper from
  1689→    day one so the pattern doesn't keep compounding.

  1720→8. The Messaging Gateway
  1721→
  1722→As designed and largely confirmed in the real code: sendMessageToGuest,
  1723→sendMessageToOwner, and sendPlatformMessage in modules/whatsapp/send.ts are the
  1724→only sanctioned paths to send an outbound message.
  1725→
  1726→  - sendMessageToGuest / sendMessageToOwner use the tenant's own Evolution
  1727→    instance and per-tenant token.
  1728→  - sendPlatformMessage uses a dedicated platform Evolution instance (separate
  1729→    credentials: PLATFORM_INSTANCE_NAME/PLATFORM_INSTANCE_TOKEN/PLATFORM_PHONE)
  1730→    — used only for Super Admin invites and broadcasts, so a tenant never
  1731→    appears to message itself with platform content.
  1732→  - Every send should log to a message/audit table and degrade gracefully (never
  1733→    throw) on failure — this was the original design and should be verified
  1734→    present on every call site as part of the assembly pass (execution-plan.md
  1735→    Track A).
  1736→
  1737→Confirmed gaps against the original design intent: rate limiting (protecting a
  1738→tenant's WhatsApp session from bulk-send bans) and retry-with-backoff on
  1739→transient failures are not confirmed present in the code as shown. Campaign
  1740→sends are currently sequential with no throttle — acceptable at pilot scale, a
  1741→real risk once a tenant has hundreds of guests in one campaign.

  1743→9. The AI Concierge
  1744→
  1745→Grounding rule (enforced by construction, confirmed in the real implementation):
  1746→the model composes language; every fact comes from a tool call or the knowledge
  1747→base.
  1748→
  1749→  - Quick Answers first. Structured facts (hours, parking, dress code,
  1750→    dietary/halal, pets, wifi, kids, location, payment) live as jsonb on
  1751→    tenants.knowledgeBase and are checked by a dedicated getQuickAnswers tool
  1752→    before the model reaches for RAG — instant, reliable answers to the
  1753→    questions guests ask most.
  1754→  - Tools for structured, changing data. getMenu, getBusinessInfo, getSpecials,
  1755→    getLoyaltyBalance query the live database directly — never RAG, so prices
  1756→    and hours are never stale.
  1757→  - RAG for unstructured knowledge. searchKnowledge embeds the guest's question
  1758→    and retrieves the top-N most similar chunks from knowledge_chunks, scoped by
  1759→    tenant_id. The knowledge ingestion pipeline (URL via Jina Reader, or PDF via
  1760→    unpdf) chunks, embeds, and stores; a re-ingest path refreshes a URL source
  1761→    when the underlying site changes.
  1762→  - Transparency in testing. The Settings → Concierge test box shows not just
  1763→    the answer but the exact snippets and similarity scores it used — a
  1764→    genuinely good verification tool, worth keeping and eventually exposing (in
  1765→    a limited form) to owners as ongoing trust-building.
  1766→  - Failure mode: if the AI call errors for any reason, the router falls back to
  1767→    a hardcoded keyword menu rather than leaving the guest unanswered —
  1768→    confirmed present and correct.
  1769→
  1770→The booking sub-engine
  1771→
  1772→A distinct, more complex piece worth documenting on its own: generateObject
  1773→extracts {date, time, partySize, occasion, specialRequests} from free text
  1774→(resolving relative dates like "Friday" against the current date); a
  1775→booking_drafts row persists partial progress across multiple messages with
  1776→a 30-minute TTL; once all required fields are present, the deterministic
  1777→modules/reservations service creates the real reservation (never the AI
  1778→directly) and a confirmation is sent. Cancel and reschedule reuse the same draft
  1779→mechanism (reschedule_of links a draft back to the reservation being changed).
  1780→
  1781→10. The Router
  1782→
  1783→As built: routeInboundMessage(tenantId, phone, text) is an ordered function, not
  1784→a data-driven engine. Confirmed order, and the reasoning behind it:
  1785→
  1786→1.  Deterministic keywords: JOIN, BALANCE/POINTS, REDEEM, STOP/UNSUBSCRIBE,
  1787→    WAITLIST
  1788→2.  CANCEL / RESCHEDULE — checked before general booking-intent matching,
  1789→    because phrases like "cancel my booking" contain a booking keyword and would
  1790→    otherwise be mis-routed
  1791→3.  CONFIRM / YES — tries waitlist-acceptance first, then
  1792→    attendance-confirmation; falls through if neither applies
  1793→4.  Continue an in-progress booking or reschedule draft
  1794→5.  New booking intent (keyword-hint match)
  1795→6.  Post-meal review-reply capture (only within a 48h window of a review
  1796→    request)
  1797→7.  Grounded AI concierge
  1798→8.  Hardcoded fallback menu, on any concierge error
  1799→
  1800→Recommendation: keep this exact pattern — it is simple, debuggable, and each
  1801→step is independently testable — but as more automations are added, extract each
  1802→numbered step into a small named matcher function (already mostly true) with a
  1803→single top-level ordered list, so the ordering rationale (like the
  1804→CANCEL-before-booking-intent case) is documented in one place rather than
  1805→implied by code position alone. This is not a recommendation to introduce a
  1806→generic automation_rules table — that abstraction doesn't fit how deterministic
  1807→these first several steps genuinely are, and would add indirection without a
  1808→real benefit until (if ever) the router needs to be edited by non-developers.
